# init-flow

One idempotent pass that turns an existing project into an agent-ready one:

1. `AGENTS.md` → linked to `template/AGENTS.md`
2. `PROJECTS.md` + `.specific/` → generated by `ingest-project`
3. `.harness/` → linked to this repo's `.harness/` via `create-relative-link`
4. `.specific/workflow.yaml` + `.specific/extensions.yml` + `.agents/skills/*` → installed by `setup-workflow`
5. Constitution → generated by `speckit-constitution` after the workflow skills are linked
6. `.specific/common.yaml` + common skill links → installed by `setup-common`

Re-running is safe: identical links are skipped, generated files are compared before writing, and nothing in the project's source tree is modified.

## When to use

- User runs `/init-flow <target_project>`
- User says: "init this project", "onboard this repo", "set up agent context here"
- A project already has code and needs `AGENTS.md`, `PROJECTS.md`, and the workflow skills

## When NOT to use

- Brand-new empty project with no code — ask first; `PROJECTS.md` will be mostly `TBD`
- User only wants one piece — run `create-relative-link`, `ingest-project`, or `setup-workflow` directly
- Target is this skills repository itself — refusing avoids linking templates into their own source

## Inputs

1. **`target_project`** — positional argument (`$TARGET_PROJECT`), or ask if empty. Expand `~`, resolve to an absolute path, and verify it is an existing directory. Abort otherwise.
2. **`source_root`** — this skills repository. Resolve once and reuse:
   ```sh
   SOURCE_ROOT="$(git -C "<skill-dir>" rev-parse --show-toplevel)"
   ```
   If git fails, fall back to the parent of the directory containing this skill. Required files:
   - `template/AGENTS.md`
   - `template/PROJECTS.template.md`
   - `template/input/project.template.yaml`
   - `template/input/workflow.template.yaml`
   - `template/output/project-features.template.yaml`
   - `template/output/extensions.template.yaml`
   - `template/LOGS.template.md`
   - `.harness/`
   - `workflow-skills/*/`

If `target_project` resolves to `source_root` or a path inside it, abort and say why.

## Steps

1. **Validate.** Resolve both paths. Confirm `target_project` is a directory and `source_root` contains `template/AGENTS.md` and at least one `workflow-skills/*/`. Stop with a clear message if any check fails.

2. **Link `AGENTS.md`.** Activate `create-relative-link` with:
   - `file_link` = `./template/AGENTS.md`
   - `target_project` = `<target_project>`
   - `target_file` = `AGENTS.md`

   It computes a relative link, prompts once before overwriting (default `Y`), and refuses to delete directories. Verify afterwards:
   ```sh
   test -L "<target_project>/AGENTS.md" && readlink -f "<target_project>/AGENTS.md"
   ```
   The resolved path must be `<source_root>/template/AGENTS.md`.

3. **Generate project context.** Activate `ingest-project` with `<target_project>` as its argument. It is read-only on the source tree and writes only:
   - `<target_project>/PROJECTS.md`
   - `<target_project>/.specific/project-features.yaml`
   - `<target_project>/.specific/project.yaml` (merged: architecture + `skills`, user fields preserved)
   - `<target_project>/LOGS.md` (seeded from `template/LOGS.template.md` when absent)

   Gate before continuing:
   - `PROJECTS.md` exists
   - `grep -q '<<' PROJECTS.md` finds nothing (no unresolved template placeholders)
   - `.specific/project-features.yaml` exists
   - `.specific/project.yaml` parses as YAML

   If `ingest-project` reports `TBD` values, collect them for the final summary — do not invent values.

4. **Link `.harness/`.** Activate `create-relative-link` with:
   - `file_link` = `.harness`
   - `target_project` = `<target_project>`
   - `target_file` = `.harness`

   The source is a directory; the skill computes a relative target (`<REL>/.harness`), prompts once before overwriting an existing link or file (default `Y`), and refuses to delete a real directory. Verify afterwards:
   ```sh
   test -L "<target_project>/.harness" && readlink -f "<target_project>/.harness"
   ```
   The resolved path must be `<source_root>/.harness`.

5. **Set up the workflow.** Activate `setup-workflow` with `<target_project>` as its argument. It seeds `.specific/workflow.yaml`, renders the per-project `.specific/extensions.yml` and `.specific/constitution.yaml` from config, and links the `workflow-skills/*` selected by config into `.agents/skills/`. It never writes through the `.harness` symlink: with `.harness` linked, `setup_specify.py` runs in linked mode (runtime install skipped, `LINKED .harness` reported); the hash-manifest copy install runs only when the destination is a real directory (fallback). It handles its own conflict prompt once per batch.

   Gate before continuing:
   - `.specific/workflow.yaml` exists
   - `.harness/init-options.json` and `.harness/workflows/workflow-registry.json` parse as JSON (through the link, or after the copy fallback)
   - `.specific/extensions.yml` parses as YAML
   - a re-run of `setup-workflow` reports no `add`/`update`/`conflict` entries

    If `setup-workflow` reports `speckit.enabled: false`, record that in the summary and continue.

5b. **Generate the constitution.** Now that `speckit-constitution` is linked under `.agents/skills/`, activate it (with no arguments) to populate `.specific/constitution.yaml` from repo context (README, PROJECTS.md) as valid YAML. Do **not** write `.harness/memory/constitution.md` — the constitution lives only in `.specific/constitution.yaml` (per taste). If the user supplied constitution principles, pass them as the argument instead. Record the resulting version (or `TODO` items) in the final report.

5c. **Set up common skills.** Activate `setup-common` with `<target_project>` as its argument. It seeds `.specific/common.yaml` (never overwrites an existing one), then links the `common-skills/*` selected by config into `.agents/skills/` (empty selection = all). It handles its own conflict prompt once per batch.

    Gate before continuing:
    - `.specific/common.yaml` exists and parses as YAML
    - a re-run of `setup-common` reports no `add`/`update`/`replace`/`conflict` entries (only `same`/`skip_linked`/`skip_real_dir`)

    If `setup-common` reports `SKIP_REAL_DIR` entries, record them in the summary (never deleted).

6. **Verify the result.**
   - Every `.agents/skills/*` entry is a symlink whose `readlink -f` resolves under `$SOURCE_ROOT/workflow-skills/` or `$SOURCE_ROOT/common-skills/`
   - `.agents/skills` contains exactly one link per selected workflow skill and per selected common skill (pre-existing unrelated entries are left alone)
   - `AGENTS.md` resolves to `template/AGENTS.md`
   - `PROJECTS.md` has no `<<...>>` and points at `@.specific/project-features.yaml`
   - `.specific/project-features.yaml` parses as YAML and has a non-empty `features` list
   - Any `detail` path listed in `.specific/project-features.yaml` resolves under `.specific/features/`
   - `.specific/workflow.yaml` exists and parses as YAML
   - `.specific/common.yaml` exists and parses as YAML
   - `.harness` is a relative symlink whose `readlink -f` resolves under `$SOURCE_ROOT/.harness` (copy fallback: a real directory containing the runtime)
   - `.harness/` contains `scripts/`, `templates/`, and `workflows/`; `.specific/constitution.yaml` exists

7. **Report.** List, per step: linked path (or "already linked"), written path (or "unchanged"), the `.harness` link (or copy-fallback installed/updated counts), linked/skipped workflow + common skills, and every `TBD` the user should fill in. Keep it terse.

## Re-running

| Situation | Behavior |
|---|---|
| Link already points at the same source | Skip silently |
| Link points elsewhere | Include in the single overwrite prompt (default `Y`) |
| Destination is a real directory | Skip, report, never delete |
| `PROJECTS.md` byte-identical | Skip and say "unchanged" |
| `PROJECTS.md` differs | Show diff, ask once (default `Y`) |
| `.specific/*.yaml` exists | Leave untouched (human-curated) |
| `.harness` symlink already points at this repo | Skip silently |
| `.harness` symlink points elsewhere | One overwrite prompt (default `Y`) |
| `.harness` destination is a real directory | Skip the link, report; `setup-workflow` installs by copy as fallback |
| `.harness` file unchanged (copy fallback) | `SAME`, no write |
| `.harness` file edited locally (copy fallback) | One keep/overwrite prompt; `keep` pins it |
| `.specific/common.yaml` exists | Leave untouched (human-curated) |
| Common skill link already points at this repo | `SKIP_LINKED` (no-op) |

## What this skill never does

- Modify, build, test, or install anything in the target's source tree
- Delete directories or force-replace a real directory with a symlink
- Commit, stage, or push
- Replace a real `.harness/` directory with a symlink — report it and keep the `setup-workflow` copy install as fallback

## Failure-degradation modes

| Failure | Behavior |
|---|---|
| `target_project` missing / not a directory | Abort before any write |
| `target_project` is `source_root` or inside it | Abort (self-link guard) |
| `source_root` or templates missing | Abort and name the missing path |
| `create-relative-link` declines overwrite | Continue with the other steps; report the skipped link |
| `.harness` destination is a real directory | `create-relative-link` aborts; report it and continue — `setup-workflow` installs `.harness/` by copy as fallback |
| `ingest-project` aborts | Keep links; report the failure and do not claim success |
| `setup-workflow` aborts | Keep completed steps; report the failing step and stderr |
| `setup-common` aborts | Keep completed steps; report the failing step and stderr |
| `workflow-skills/` empty | `setup-workflow` reports zero links; continue |
| `common-skills/` empty | `setup-common` reports zero links; continue |
| One workflow skill fails to link | Continue the rest; list the failure in the final report |
| One common skill fails to link | Continue the rest; list the failure in the final report |

## Done criteria

- `AGENTS.md` is a relative symlink to `template/AGENTS.md`
- `PROJECTS.md` exists with no placeholders and points at `.specific/project-features.yaml`
- `.specific/project-features.yaml` exists and parses
- `.specific/workflow.yaml` exists and parses
- `.specific/common.yaml` exists and parses
- `.harness` is a relative symlink resolving to this repo's `.harness/` (copy fallback: fully installed) and a re-run is a no-op (`LINKED` / `SAME`)
- `.agents/skills/` holds one relative symlink per selected workflow skill and per selected common skill
- Final report lists every `TBD` and every skip

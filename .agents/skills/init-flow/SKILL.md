# init-flow

One idempotent pass that turns an existing project into an agent-ready one:

1. `AGENTS.md` → linked to `template/AGENTS.md`
2. `PROJECTS.md` + `.specific/` → generated by `ingest-project`
3. `.specify/` + `.specific/workflow.yaml` + `.agents/skills/*` → installed by `setup-workflow`

Re-running is safe: identical links are skipped, generated files are compared before writing, and nothing in the project's source tree is modified.

## When to use

- User runs `/init-flow <target_project>`
- User says: "init this project", "onboard this repo", "set up agent context here"
- A project already has code and needs `AGENTS.md`, `PROJECTS.md`, and the workflow skills

## When NOT to use

- Brand-new empty project with no code — ask first; `PROJECTS.md` will be mostly `TBD`
- User only wants one of the three pieces — run `create-relative-link`, `ingest-project`, or `setup-workflow` directly
- Target is this skills repository itself — refusing avoids linking templates into their own source

## Inputs

1. **`target_project`** — positional argument (`$TARGET_PROJECT`), or ask if empty. Expand `~`, resolve to an absolute path, and verify it is an existing directory. Abort otherwise.
2. **`source_root`** — this skills repository. Resolve once and reuse:
   ```sh
   SOURCE_ROOT="$(git -C "<skill-dir>" rev-parse --show-toplevel)"
   ```
   If git fails, fall back to the parent of the directory containing this skill. Required files:
   - `template/AGENTS.md`
   - `template/PROJECTS.template.md`
   - `template/input/project.template.yaml`
   - `template/input/workflow.template.yaml`
   - `template/output/project-features.template.yaml`
   - `template/output/extensions.template.yaml`
   - `template/LOGS.template.md`
   - `.specify/`
   - `workflow-skills/*/`

If `target_project` resolves to `source_root` or a path inside it, abort and say why.

## Steps

1. **Validate.** Resolve both paths. Confirm `target_project` is a directory and `source_root` contains `template/AGENTS.md` and at least one `workflow-skills/*/`. Stop with a clear message if any check fails.

2. **Link `AGENTS.md`.** Activate `create-relative-link` with:
   - `file_link` = `./template/AGENTS.md`
   - `target_project` = `<target_project>`
   - `target_file` = `AGENTS.md`

   It computes a relative link, prompts once before overwriting (default `Y`), and refuses to delete directories. Verify afterwards:
   ```sh
   test -L "<target_project>/AGENTS.md" && readlink -f "<target_project>/AGENTS.md"
   ```
   The resolved path must be `<source_root>/template/AGENTS.md`.

3. **Generate project context.** Activate `ingest-project` with `<target_project>` as its argument. It is read-only on the source tree and writes only:
   - `<target_project>/PROJECTS.md`
   - `<target_project>/.specific/project-features.yaml`
   - `<target_project>/.specific/project.yaml` (merged: architecture + `skills`, user fields preserved)
   - `<target_project>/LOGS.md` (seeded from `template/LOGS.template.md` when absent)

   Gate before continuing:
   - `PROJECTS.md` exists
   - `grep -q '<<' PROJECTS.md` finds nothing (no unresolved template placeholders)
   - `.specific/project-features.yaml` exists
   - `.specific/project.yaml` parses as YAML

   If `ingest-project` reports `TBD` values, collect them for the final summary — do not invent values.

4. **Set up the workflow.** Activate `setup-workflow` with `<target_project>` as its argument. It seeds `.specific/workflow.yaml`, installs/refreshes `.specify/` from the hash manifest, renders the constitution/extension hooks/registry, and links the `workflow-skills/*` selected by config into `.agents/skills/`. It handles its own conflict prompt once per batch.

   Gate before continuing:
   - `.specific/workflow.yaml` exists
   - `.specify/init-options.json` and `.specify/workflows/workflow-registry.json` parse as JSON
   - `.specific/extensions.yml` parses as YAML
   - a re-run of `setup-workflow` reports no `add`/`update`/`conflict` entries

   If `setup-workflow` reports `speckit.enabled: false`, record that in the summary and continue.

5. **Verify the result.**
   - Every `.agents/skills/*` entry is a symlink whose `readlink -f` resolves under `$SOURCE_ROOT/workflow-skills/`
   - `.agents/skills` contains exactly one link per selected workflow skill (pre-existing unrelated entries are left alone)
   - `AGENTS.md` resolves to `template/AGENTS.md`
   - `PROJECTS.md` has no `<<...>>` and points at `@.specific/project-features.yaml`
   - `.specific/project-features.yaml` parses as YAML and has a non-empty `features` list
   - `.specific/workflow.yaml` exists and parses as YAML
   - `.specify/` contains `scripts/`, `templates/`, `memory/constitution.md`, and `workflows/`; `.specific/constitution.yaml` exists

6. **Report.** List, per step: linked path (or "already linked"), written path (or "unchanged"), installed/updated `.specify` counts, linked/skipped skills, and every `TBD` the user should fill in. Keep it terse.

## Re-running

| Situation | Behavior |
|---|---|
| Link already points at the same source | Skip silently |
| Link points elsewhere | Include in the single overwrite prompt (default `Y`) |
| Destination is a real directory | Skip, report, never delete |
| `PROJECTS.md` byte-identical | Skip and say "unchanged" |
| `PROJECTS.md` differs | Show diff, ask once (default `Y`) |
| `.specific/*.yaml` exists | Leave untouched (human-curated) |
| `.specify` file unchanged | `SAME`, no write |
| `.specify` file edited locally | One keep/overwrite prompt; `keep` pins it |

## What this skill never does

- Modify, build, test, or install anything in the target's source tree
- Delete directories or force-replace a real directory with a symlink
- Commit, stage, or push
- Vendor `.specify/` itself — `setup-workflow` owns that install and its manifest
- Link `common-skills/*` — those are opt-in per project, not part of init

## Failure-degradation modes

| Failure | Behavior |
|---|---|
| `target_project` missing / not a directory | Abort before any write |
| `target_project` is `source_root` or inside it | Abort (self-link guard) |
| `source_root` or templates missing | Abort and name the missing path |
| `create-relative-link` declines overwrite | Continue with the other steps; report the skipped link |
| `ingest-project` aborts | Keep links; report the failure and do not claim success |
| `setup-workflow` aborts | Keep completed steps; report the failing step and stderr |
| `workflow-skills/` empty | `setup-workflow` reports zero links; continue |
| One workflow skill fails to link | Continue the rest; list the failure in the final report |

## Done criteria

- `AGENTS.md` is a relative symlink to `template/AGENTS.md`
- `PROJECTS.md` exists with no placeholders and points at `.specific/project-features.yaml`
- `.specific/project-features.yaml` exists and parses
- `.specific/workflow.yaml` exists and parses
- `.specify/` is fully installed and a re-run is a no-op
- `.agents/skills/` holds one relative symlink per selected workflow skill
- Final report lists every `TBD` and every skip

## References

- `template/AGENTS.md` — the linked entry point; loads `@PROJECTS.md`
- `template/PROJECTS.template.md` — rendered by `ingest-project`
- `template/input/project.template.yaml` — seeds `.specific/project.yaml`
- `template/input/workflow.template.yaml` — seeds `.specific/workflow.yaml`
- `template/output/project-features.template.yaml` — seeds `.specific/project-features.yaml`
- `template/output/extensions.template.yaml` — render base for `.specific/extensions.yml`
- `create-relative-link` — relative symlink contract used in step 2
- `ingest-project` — the context generator used in step 3
- `setup-workflow` — the `.specify` + workflow-skill installer used in step 4
